# 0001 — Peer-novelty state extends `LearnedState`, not a new file

## Context

`AN-D1` (`docs/specs/an-d1-peer-novelty-plan.md`) needs the guard to remember, per (pod, metric), whether a
peer deviation is a known-stable characteristic or a new/changing one, so it does not re-alert on a fixed
configuration difference forever. The client decided 2026-08-10 that this memory must survive a guard
restart — routine rollouts are already measured to disturb the guard (`aiops-backlog.md`, A5), and losing the
memory on every restart would reproduce a bounded copy of the exact noise this mechanism exists to remove.
That makes the on-disk shape of this state a decision this repository treats as hard to reverse (`docs/adr/README.md`).

## Forces

- `LearnedState` already persists two things of the same character — "what this cluster does when nothing is
  wrong" — in one payload, using a positional, forward-compatible section format: a missing or unreadable
  section cold-starts only that part, never the whole payload (`LearnedState.cs:20-22`).
- `FloorCalibrator` was bitten by exactly this class of bug once already: a file written by an older build
  could be silently read as satisfying a minimum-observations gate it never actually recorded. The fix was an
  explicit `#windows` marker (`FloorCalibrator.cs:46-51`) — two columns, so an old reader skips the new field
  on a column-count guard rather than misreading it. The fix that caught the original bug was a test built
  from a **real** old-format fixture; a fixture generated by the fixed code could not have failed.
- Peer-novelty state must **not** resurrect stale history for a reused pod name. A StatefulSet pod restarting
  keeps its name but gets a new `PodPlacement.CreatedAt` — the design already resets in-memory state on that
  change (`an-d1-peer-novelty-plan.md`, section 5); persistence must carry the same defence, or a restart
  reintroduces the exact bug the reset exists to prevent, just delayed until the next guard restart.
- The state is population-scaled (bounded per live pod, pruned against the roster), the same shape `_silent`
  and `MetricHistory` already are, not a small human-authored table.
- The mechanism covers both `MetricIndex` built-in channels and `CustomMetricBinding` channels
  (`AnomalyGuard.RunPeer` and `AnomalyGuard.RunCustomPeer` both call `IncidentPipeline.ObservePeerGroup` —
  confirmed by `mcp__overfit-navigator__find_callers`/`find_references`, `an-d1-peer-novelty-plan.md` section
  0), so the persisted row must key on both without a custom channel name colliding with a built-in one.
  `FloorCalibrator` already solved this for its own persisted state with a `CustomMarker` prefix
  (`FloorCalibrator.cs:40-43`); the new format reuses that convention rather than inventing a second one.

## Options considered

1. **A new, separate persisted file/section**, the way open incidents get their own format
   (`PersistedIncident`).
2. **Extend `LearnedState`'s existing text payload** with a fourth section (`### peer-novelty`), following its
   established positional, forward-compatible convention.
3. **Fold it into `MetricHistory`**, adding a pod dimension to the existing workload-keyed store.

Option 3 was rejected during the architecture review itself (`an-d1-peer-novelty-plan.md`, finding 3):
`MetricHistory`'s reset boundary is multi-day and per-workload; this state's reset boundary is per-pod and
tied to `CreatedAt`. Overloading one type with two incompatible reset policies is a defect waiting to be
written, not a simplification.

## Decision

**Option 2.** Add a fourth section to `LearnedState`'s payload, `### peer-novelty`, parsed positionally exactly
as `### labels` and `### suppressions` already are — an old payload simply has no such section and the new
part cold-starts, the same graceful degradation already proven for the two sections added after the original
format shipped.

Each persisted row carries, at minimum: pod, metric, the gap-history ring this pod/metric has accumulated (see
Amendment below for its shape), and the pod's `PodPlacement.CreatedAt` **as recorded at write time**. On
restore, a row is only adopted if the roster's current `CreatedAt` for that pod name matches the recorded one;
a mismatch is treated exactly like a pod the guard has never seen before (empty history, fail-open to
reporting) — never as a silent inheritance of the previous incarnation's learning.

## Rationale

- Matches `LearnedState`'s own stated design principle — "two things, one file... unlike incidents, which get
  their own" (`LearnedState.cs:14-18`) — because peer-novelty state is the same category of thing (what
  normal looks like) as history and calibration, not an incident's own independent lifetime.
- Reuses a parsing convention already exercised in production rather than inventing a new one, which is where
  `FloorCalibrator`'s own bug was introduced the first time.
- The `CreatedAt` echo is the direct, minimal fix for the reused-pod-name risk, applying the same idea the
  `#windows` marker used: record the fact that would otherwise be silently assumed, so a mismatch is
  detectable instead of invisible.

## Consequences

- `LearnedState.Write`/`Read` gain a fourth section and must keep the same "either half may come back empty;
  neither throws" guarantee the other three already give.
- **A test must read a real pre-this-change `LearnedState` payload** (not one generated by the new code) and
  confirm history, calibration, labels and suppressions all still restore untouched — the same lesson the
  `#windows` bug taught: a fixture produced by the fixed code cannot exercise the bug it fixes.
- Every future reader of a `LearnedState` payload (tests, an ops inspection tool, a future migration) must
  know a fourth section can exist; this is the standing cost of extending a shared format rather than a new
  one, accepted because the alternative (a fifth persisted file) duplicates the graceful-degradation logic
  this format already has for free.
- The exact row layout (which fields beyond pod/metric/CreatedAt/history) is left to implementation and does
  not need a further ADR — only the decision to live inside `LearnedState`'s section convention and to carry
  `CreatedAt` for the reuse check is the part being fixed here.

## Amendment, 2026-08-10 — the in-memory shape is a ring, not `BoundedSamples`

Flagged by the developer during implementation, verified in source, approved. Not a silent edit — the reasons
are the durable part, and this ADR's persisted-row shape (Decision, above) depends on them.

**`BoundedSamples` (`Sources/Main/Statistics/BoundedSamples.cs`) cannot carry the per-pod gap history it was
originally assumed to hold, for three specific reasons:**

1. It stores values only (`private double[] _values`) — `TrendDetector.Detect` requires an index-aligned
   `timestampsSeconds` span, which `BoundedSamples` has no field for.
2. `Add` silently drops non-finite values, so two parallel `BoundedSamples` instances (one for gaps, one for
   timestamps) would desynchronise the moment a sample is missing — exactly the cycle the pairing matters most.
3. Its decimation is systematic halving spread across the whole stream: correct semantics for "a floor set
   from a maximum, representative of all history" (its original job in `FloorCalibrator`), wrong semantics for
   "has the gap changed *recently*", which is what this mechanism asks every cycle.

**Replacement**: a fixed-capacity ring of `(timestampSeconds, gap)` pairs, persisted in the same
`CustomMarker`/column-guard style this ADR already requires for the rest of the row. Two correctness
properties follow directly from the three reasons above and are required of the persisted format, not just
the in-memory one:

- The ring's capacity must be documented as a **wall-clock** statement (`capacity × cycle cadence` is the
  window the trend sees) — the same cadence-vs-days-vs-scrape unit trap named in
  `an-d1-peer-novelty-plan.md` section 6, arriving here a fourth time.
- A non-finite gap drops **its timestamp atomically** with it, on both the in-memory ring and the persisted
  row — the direct fix for reason 2, and it must survive a write/read round trip or the persisted state
  reintroduces the desynchronisation the ring was built to prevent.

Spike 1 (`an-d1-peer-novelty-plan.md` section 7) passed against this shape on the real recorded `pj7r8` gap
series before this amendment was needed to persist it — the shape choice is validated on real data, only the
storage type underneath it changed.

## Status

Accepted, 2026-08-10 (client decision: persist across restart; `overfit-architect`: format extends
`LearnedState`); amended same day (ring buffer replaces `BoundedSamples`, developer-flagged,
architect-approved). Contingent on `AN-D1`'s mechanism itself proceeding — if the mechanism is later
abandoned, this record still stands as the correct shape had it shipped.
